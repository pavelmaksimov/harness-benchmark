# Чекпоинты Task Manager benchmark

## Цель

Траектория измеряет, насколько далеко агент может развить один бэкенд и сохранить прежнее поведение. Работа начинается с пустого каталога решения и проходит через 15 законченных функций продукта. Реализация — REST API на Python 3.12 с FastAPI, SQLAlchemy 2 и SQLite. Клиентская часть, офлайн-режим, синхронизация и внешние сервисы в задачу не входят.

Первый чекпоинт намеренно крупнее остальных: после него уже остается полезное приложение. Каждый следующий чекпоинт добавляет одну законченную функцию; сложность в среднем возрастает.

## Чекпоинты

### 1. Работающий личный менеджер задач

Создать приложение с нуля и предоставить его как `task_manager.main:app`.

- Пользователь может зарегистрироваться по email и паролю, войти и получить JWT.
- В базе хранится хеш пароля, а не исходный пароль.
- При регистрации создается по одному состоянию категорий `todo`, `in_progress`, `done` и `canceled`; состояние `todo` становится начальным.
- Авторизованный пользователь может создать, получить, изменить и вывести список задач с обязательным заголовком, необязательным описанием и состоянием.
- Одна учетная запись не может читать или менять данные другой.
- Данные сохраняются в SQLite после перезапуска приложения.
- Удаление задач в этот чекпоинт не входит.

### 2. Проекты и Входящие

Добавить необязательную группировку по проектам, не меняя основной контракт задачи.

- Задача без проекта относится к системным Входящим.
- Пользователь может создать, получить, переименовать, архивировать и восстановить проект, а также вывести список проектов.
- Задачу можно переносить между проектами и Входящими.
- Архивированный проект и его задачи доступны для чтения, но не принимают новые задачи и любые изменения до восстановления проекта.
- Проекты не удаляются.

### 3. Даты и точное время срока

Добавить полную семантику срока задачи.

- У задачи может быть либо календарная дата, либо точный момент со смещением часового пояса, но не оба значения сразу.
- У каждой учетной записи есть часовой пояс IANA для толкования календарных дат.
- Задача с календарной датой становится просроченной после окончания этого дня в часовом поясе учетной записи.
- Задача с точным сроком становится просроченной после наступления указанного момента.
- Переход в состояние категории `done` или `canceled` исключает задачу из просроченных, не стирая срок.
- Некорректные даты, часовые пояса, смещения и конфликтующие поля отклоняются.

### 4. Выборки задач

Сделать список задач пригодным для работы без добавления новых полей задачи.

- Задачи фильтруются по проекту или Входящим, пользовательскому состоянию, системной категории, диапазону срока и признаку просрочки.
- Результаты сортируются по времени создания, времени изменения, заголовку или сроку в любом направлении.
- Постраничная выдача по курсору использует однозначное дополнительное поле сортировки, не дублирует и не пропускает неизмененные записи.
- Фильтры, сортировка и постраничная выдача сочетаются в одном запросе.
- Все выборки ограничены текущей учетной записью.

### 5. Пользовательские состояния

Превратить четыре начальных состояния в настраиваемый общий процесс пользователя.

- Пользователь может добавлять, переименовывать и упорядочивать состояния, общие для всех его проектов.
- Каждое состояние относится ровно к одной из четырех системных категорий; к одной категории может относиться несколько состояний.
- В учетной записи всегда остается хотя бы одно состояние каждой системной категории.
- Ровно одно состояние категории `todo` является начальным; пользователь может его сменить.
- Между любыми состояниями можно переходить свободно, без графа разрешенных переходов.
- Удаление состояния требует явной замены: все затронутые задачи переносятся, а состояние удаляется одной неделимой операцией.

### 6. Порядок на канбан-доске

Добавить устойчивый ручной порядок, независимый от сортировки обычной выборки.

- На доске есть отдельная колонка для каждого пользовательского состояния, даже если несколько состояний относятся к одной системной категории.
- У каждой задачи есть устойчивая ручная позиция внутри текущей колонки.
- Пользователь может поставить задачу до, после или между соседними задачами либо перенести ее в другую колонку одной операцией.
- Новая задача или перенос без указанного соседа помещает задачу в конец колонки.
- Уплотнение позиций незаметно для клиента: повторное чтение сохраняет заданный порядок, а позиции остаются уникальными.

### 7. Оптимистичный контроль версий

Не позволять двум HTTP-запросам незаметно перезаписать изменения одной задачи.

- Каждая задача содержит монотонно растущую версию.
- Изменяющий запрос передает версию, на основе которой он был сформирован.
- Совпавшая версия применяет изменение и увеличивает версию ровно один раз.
- Устаревшая версия ничего не меняет и возвращает `409` с текущим представлением задачи.
- Операция над несколькими задачами увеличивает версию каждой действительно измененной задачи.

### 8. Дерево задач

Добавить подзадачи произвольной глубины как одну цельную функцию.

- Задачу можно присоединить к другой задаче или снова сделать корневой.
- Задача не может стать собственным предком.
- Вся ветвь целиком относится к одному проекту либо Входящим.
- Перенос ветви между проектами или Входящими переносит всех потомков одной неделимой операцией.
- Родителя нельзя перевести в `done`, пока хотя бы один потомок не находится в `done` или `canceled`; ошибка перечисляет блокирующие задачи.
- В остальных случаях состояния родителя и потомков независимы; завершение родителя не завершает потомков автоматически.

### 9. Удаление и восстановление задач

Добавить обратимое удаление, сохранив целостность дерева.

- Удаление задачи логически удаляет всю ее ветвь одной операцией.
- Удаленные задачи не попадают в обычные списки, доски, просроченные задачи и последующую аналитику.
- Отдельная Корзина возвращает удаленные корни и их потомков.
- Восстановление удаленного корня возвращает всю ветвь с проектом, состояниями, иерархией и относительным порядком.
- Восстановление в архивированный проект запрещено до восстановления проекта.
- Повторное удаление или восстановление безопасно и не оставляет частично измененную ветвь.

### 10. Неизменяемая история задач

Записывать значимые изменения, не превращая приложение в систему, где состояние восстанавливается из событий.

- Создание, редактирование, перемещение, завершение, отмена, удаление и восстановление задачи добавляют записи истории.
- Запись содержит задачу, вид изменения, время и относящиеся к изменению старые и новые значения.
- Операция над ветвью создает записи для каждой измененной задачи.
- История имеет однозначный порядок, остается доступной для удаленных задач и не меняется через API.
- Текущие строки задач остаются источником истины; история нужна для аудита и аналитики, но не для отмены изменений.

### 11. Внутренние напоминания

Создавать надежные внутренние уведомления для задач с точным сроком.

- Напоминания доступны только для точного срока; календарная дата уведомление не создает.
- Повторная обработка наступивших сроков создает не более одного уведомления для сочетания задачи и срока.
- Изменение будущего срока отменяет старое ожидающее напоминание и назначает новое.
- Уведомление принадлежит владельцу задачи и имеет состояния «прочитано» и «не прочитано».
- Пользователь может вывести уведомления и отметить их прочитанными.
- Email, push, webhook и внешняя очередь в задачу не входят.

### 12. Повторяющиеся задачи

Заранее создавать экземпляры повторения с однозначным календарным поведением.

- Поддерживаются правила: каждые N дней, каждые N недель в выбранные дни недели и каждые N месяцев в выбранный день.
- Если выбранного числа нет в коротком месяце, используется последний день месяца.
- Экземпляры поддерживаются на 90 дней вперед; повторный запуск не создает дублей.
- Повторяющаяся задача должна быть корневой и не иметь потомков; ее нельзя включить в дерево задач.
- Созданные экземпляры остаются обычными изменяемыми задачами, связанными со своим повторением.
- Изменение правила сохраняет завершенные и вручную измененные экземпляры, удаляет нетронутые будущие экземпляры и заново строит горизонт одной неделимой операцией.
- Если правило содержит точное время, созданные задачи используют уже существующее поведение сроков и напоминаний.

### 13. Фиксированная аналитика

Добавить полезные отчеты до появления общего языка отчетов.

- За выбранный период API возвращает текущие количества по проекту, пользовательскому состоянию и системной категории.
- API возвращает число завершенных задач по дням, среднее и медианное время от создания до `done`, а также текущий список просроченных задач.
- Завершение определяется по истории; при выходе из `done` и повторном входе применяется явно описанное правило последнего завершения.
- Удаленные задачи исключаются, а архивированные проекты остаются доступны аналитике.
- Для пустых групп и периодов определен однозначный результат.

### 14. Сохраненные отчеты

Позволить сохранять параметризованные варианты фиксированной аналитики.

- Пользователь может создать, получить, переименовать, изменить, удалить и выполнить определение отчета, а также вывести список определений.
- Определение выбирает один фиксированный отчет и поддерживаемые им параметры периода, проекта, состояния и категории.
- Определения принадлежат учетной записи; сочетания параметров проверяются при записи.
- Хранится только определение, а результат при каждом выполнении заново рассчитывается по текущим задачам и истории.
- Удаление определения не удаляет задачи или историю.

### 15. Общий конструктор отчетов

Заменить выбор фиксированного отчета безопасным составным контрактом, сохранив возможности чекпоинтов 13 и 14.

- Разрешенные измерения: проект, пользовательское состояние, системная категория и временной интервал по дням, неделям или месяцам.
- Разрешенные показатели: количество задач, созданных, завершенных и просроченных задач, а также среднее или медианное время завершения.
- Разрешенные фильтры: период, проект, пользовательское состояние и системная категория.
- Отчет может сочетать совместимые измерения, показатели и фильтры; некорректные и неоднозначные сочетания отклоняются с точной ошибкой.
- Разовые и сохраненные отчеты используют одинаковые правила выполнения и изоляцию учетных записей.
- Ранее сохраненные фиксированные отчеты остаются действительными.
- Произвольный SQL, пользовательские формулы и сохраненные снимки результатов в задачу не входят.

## Правила оценки

Рабочий каталог решения сохраняется между чекпоинтами, хотя контекст агента может сбрасываться. Поэтому каждый чекпоинт расширяет код всех предыдущих этапов.

SCB оценивает траекторию следующим образом:

- Тесты без маркера в файле текущего чекпоинта относятся к **Core** и задают обязательный контракт новой функции.
- Дополнительные успешные сценарии относятся к **Functionality**.
- Некорректный ввод, нарушения доступа и предметных ограничений относятся к **Error**.
- При `include_prior_tests: true` SCB повторно запускает файлы всех прошлых чекпоинтов и относит результаты к **Regression**.
- Политика `all-core-cases` останавливает траекторию только при ошибке Core текущего чекпоинта.

Успех чекпоинта не означает, что прошла вся регрессия. В отчетах Core, Functionality, Error и Regression показываются отдельно, чтобы более длинная траектория со сломанным прежним поведением не считалась автоматически лучшей. Единый взвешенный балл не вводится.

API проверяется через ASGI TestClient по `task_manager.main:app`; отдельно проверяется запуск приложения через Uvicorn. В тестах времени срок, напоминания, повторения и аналитика управляются явно: ожидание фоновых циклов по настоящим часам не используется.
