# Task Manager: накопительная задача бенчмарка

Метка: `ready-for-agent`

## Problem Statement

Автору эксперимента нужна воспроизводимая накопительная задача (на базе SlopCodeBench), которая измеряет, насколько далеко агент способен развить один полезный backend и при этом сохранить ранее реализованное поведение. Сейчас предметный словарь, форма эксперимента и границы 15 чекпоинтов согласованы, но отсутствуют однозначные задания чекпоинтов, каркас задачи, проверочные сценарии и эталонная реализация.

Без общего HTTP-контракта и единого способа управлять временем разные чекпоинты могут противоречить друг другу, а тесты — случайно оценивать детали реализации вместо внешнего поведения. Это сделает сравнение baseline и harness-вариантов недостоверным.

## Solution

Создать новую накопительную задачу для личного менеджера задач. Все варианты эксперимента начинают с пустого каталога решения и получают одинаковые 15 заданий. Первый чекпоинт сразу дает работающий REST API с регистрацией, JWT и базовыми операциями с задачами; каждый следующий добавляет одну законченную возможность.

Зафиксировать единый HTTP-контракт для идентификаторов, времени, ошибок, авторизации, кодов ответа и постраничной выдачи. Основные проверки выполнять на наиболее высоком доступном шве — через ASGI-приложение `task_manager.main:app`. Отдельной проверкой подтверждать, что то же приложение запускается через Uvicorn. Время в проверках подменять управляемыми часами, а наступившие напоминания и повторения обрабатывать явным вызовом, без ожидания фонового цикла.

Core каждого чекпоинта проверяет только новую обязательную возможность. Успешные дополнительные сценарии относятся к Functionality, некорректный ввод и нарушения доступа — к Error, а все тесты прошлых чекпоинтов автоматически повторяются как Regression. Результаты этих четырех групп хранятся раздельно, без единого взвешенного балла.

## User Stories

1. As an автор эксперимента, I want оба варианта получать одинаковую накопительную задачу, so that измеряется влияние только исследуемого набора инструкций.
2. As an автор эксперимента, I want решение начинаться с пустого каталога, so that результат не зависит от заранее подготовленной архитектуры.
3. As an автор эксперимента, I want первый чекпоинт давать полезный работающий backend, so that глубина траектории начинается с полноценного вертикального сценария.
4. As an автор эксперимента, I want каждый следующий чекпоинт добавлять одну законченную возможность, so that причина продвижения или остановки остается понятной.
5. As an автор эксперимента, I want поздние чекпоинты в среднем быть сложнее ранних, so that траектория различает решения разного качества.
6. As an автор эксперимента, I want прежние тесты повторяться после каждого изменения, so that продвижение не скрывает поломку уже работающего поведения.
7. As an автор эксперимента, I want видеть Core, Functionality, Error и Regression отдельно, so that качество нельзя свести к вводящему в заблуждение единому баллу.
8. As an агент под испытанием, I want получать однозначный контракт каждого чекпоинта, so that мне не приходится угадывать формат API.
9. As an агент под испытанием, I want будущие возможности не упоминаться как требования ранних чекпоинтов, so that я реализую только текущую законченную функцию.
10. As a пользователь, I want зарегистрировать учетную запись по email и паролю, so that у меня появляется личное пространство данных.
11. As a пользователь, I want войти и получить JWT, so that последующие запросы выполняются от имени моей учетной записи.
12. As a пользователь, I want мой пароль храниться только в виде стойкого хеша, so that утечка базы не раскрывает исходный пароль.
13. As a пользователь, I want при регистрации получить начальные состояния `todo`, `in_progress`, `done` и `canceled`, so that приложение готово к работе без настройки.
14. As a пользователь, I want создать задачу с заголовком, описанием и состоянием, so that я могу зафиксировать личную единицу работы.
15. As a пользователь, I want получить, изменить и вывести список своих задач, so that я могу вести текущую работу.
16. As a пользователь, I want данные сохраняться в SQLite после перезапуска приложения, so that работа не теряется между запусками.
17. As a пользователь, I want данные другой учетной записи быть недоступными, so that личные задачи остаются изолированными.

## Implementation Decisions

- Задача является отдельной задачей SlopCodeBench и не изменяет существующие задачи. Решение каждого прогона начинается с пустого каталога и сохраняется между 15 чекпоинтами.
- Обязательный стек решения: Python 3.12, FastAPI, SQLAlchemy 2 и SQLite. Один backend и одна SQLite являются единственным источником истины.
- Приложение экспортируется как `task_manager.main:app`. Основной проверочный шов — HTTP-вызовы к этому ASGI-приложению. Отдельная минимальная проверка запускает тот же объект через Uvicorn на свободном порту.
- Идентификаторы всех пользовательских сущностей передаются как непрозрачные строки UUID. Клиент не должен извлекать из них порядок или иной смысл.
- Email сравнивается без учета регистра после удаления окружающих пробелов. Повторная регистрация того же нормализованного email возвращает конфликт.
- JWT передается как `Authorization: Bearer <token>`. Отсутствующий, неверный или просроченный токен возвращает `401`; доступ к существующей чужой сущности возвращает `404`, чтобы не раскрывать ее наличие.
- Пароли никогда не возвращаются через API и хранятся с солью в виде стойкого хеша. Конкретная библиотека и схема хеширования не являются частью внешнего контракта.
- Даты передаются как `YYYY-MM-DD`. Моменты времени передаются в RFC 3339 с обязательным часовым смещением; ответы нормализуют моменты в UTC и используют суффикс `Z`.
- Серверные поля `created_at` и `updated_at` задаются управляемыми часами, доступны только для чтения и имеют однозначный дополнительный порядок по идентификатору.
- Общая форма ошибки: объект `error` с устойчивым машинным `code`, понятным `message` и необязательным `details`. Ошибки проверки полей дополнительно указывают поля в `details`.
- Успешное создание возвращает `201`, чтение и изменение — `200`, успешная операция без тела — `204`. Неверный ввод возвращает `422`, отсутствие аутентификации — `401`, конфликт уникальности или версии — `409`, отсутствующая либо чужая сущность — `404`.
- Частичное изменение использует `PATCH`; отсутствующее поле не меняется, явное `null` очищает только допускающее отсутствие значение. Неизвестные поля отклоняются.
- Списки возвращают `items` и непрозрачный `next_cursor`. Отсутствие следующей страницы представляется `null`. Клиент передает `cursor` и ограниченный `limit`; курсор включает выбранные сортировку и фильтры и отклоняется при попытке применить его к другому запросу.
- Сортировка всегда имеет идентификатор как последнее дополнительное поле. Значения без срока располагаются после значений со сроком при обоих направлениях сортировки, чтобы порядок страниц оставался определенным.
- Все операции над несколькими сущностями выполняются одной транзакцией: перенос ветви, замена удаляемого состояния, логическое удаление, восстановление и перестроение горизонта повторений не оставляют частичного результата.
- Архивирование относится только к проекту. Логическое удаление относится только к задаче и ее ветви; эти понятия не подменяют друг друга.
- Текущие строки задач остаются источником истины. История изменений является неизменяемым журналом аудита и аналитики, но не используется для восстановления текущего состояния.
- Версия задачи начинается с `1`. Каждый запрос, реально изменивший задачу, увеличивает ее ровно один раз. Запрос изменения передает ожидаемую версию в теле; конфликт возвращает текущее представление задачи внутри `error.details`.
- Пользовательское состояние и системная категория остаются разными понятиями. Канбан строится по пользовательским состояниям, а аналитика может группировать по обоим уровням.
- Позиция канбан-доски является серверной деталью. Клиент задает относительное размещение через соседнюю задачу; API гарантирует только устойчивый порядок и уникальность.
- Календарная дата не создает уведомление. Точный срок создает не более одного уведомления для сочетания задачи и конкретного срока.
- Повторяющаяся задача является отдельной корневой задачей без потомков. Экземпляры повторения являются обычными задачами и содержат устойчивую ссылку на повторение и дату экземпляра.
- Для повторений, напоминаний и аналитики используется один источник текущего времени. Проверки подменяют часы процесса; решение не обязано предоставлять публичный API изменения времени.
- Наступившие сроки и горизонт повторений обрабатываются явной служебной операцией приложения. Операция использует текущие управляемые часы, является идемпотентной и не требует фонового ожидания. Она доступна только аутентифицированной учетной записи и обрабатывает только ее данные.
- Фиксированная аналитика и общий конструктор используют один исполнитель отчетов. Общий конструктор принимает только перечисленные измерения, показатели и фильтры; произвольный SQL и пользовательские формулы отсутствуют.
- Совместимость сохраненных фиксированных отчетов обеспечивается преобразованием их определений в тот же внутренний договор выполнения, которым пользуется общий конструктор.
- Конфигурация каждого чекпоинта включает прошлые тестовые файлы. Политика остановки — `all-core-cases`; раннер SlopCodeBench ради задачи не изменяется.
- Задания чекпоинтов описывают только внешний контракт текущей возможности и необходимые изменения уже известных контрактов. Они не предписывают внутренние слои, классы, шаблоны проектирования или раскладку модулей сверх обязательной точки импорта.
- Зависимости ограничиваются обязательным стеком и минимальными средствами JWT и хеширования паролей. Внешние очереди, почта, push, webhooks, офлайн-клиенты и синхронизация не добавляются.

## Testing Decisions

- Хороший тест вызывает публичный HTTP-контракт и проверяет наблюдаемый ответ, сохраненные данные или результат повторного запроса. Он не проверяет названия внутренних классов, таблиц, функций, порядок SQL-запросов или выбранный шаблон архитектуры.
- Главный тестовый шов — ASGI TestClient, импортирующий `task_manager.main:app`. Это позволяет быстро и детерминированно проверять весь HTTP-путь без отдельного процесса для каждого сценария.
- Единственный дополнительный шов процесса запуска — короткая проверка Uvicorn на свободном порту с ожиданием готовности и гарантированным завершением процесса. Она подтверждает, что обязательная точка импорта работает вне тестового процесса.
- Управляемые часы подменяют время процесса на уровне тестовой среды. Сценарии срока, напоминаний, повторений и аналитики задают точный момент явно и вызывают служебную обработку без `sleep`.
- SQLite каждого теста изолируется временным путем. Проверка сохранности повторно создает приложение или Uvicorn-процесс над тем же путем и подтверждает доступность ранее записанных данных.
- Проверки учетных записей всегда создают как минимум двух пользователей и пытаются читать либо менять данные через второй JWT. Внешний результат для чужой сущности совпадает с отсутствующей сущностью.
- Многошаговые REST-сценарии используют данные случаев и сохранение значений предыдущих ответов по образцу существующей задачи `trajectory_api`. Общие помощники ограничиваются отправкой запросов, подстановкой сохраненных значений и проверкой схемы ответа.
- Текущий тестовый файл без маркера содержит Core — минимальный обязательный путь новой возможности.
- Дополнительные успешные варианты текущего чекпоинта помечаются Functionality. Некорректный ввод, нарушения владения и предметных ограничений помечаются Error.
- Прошлые тестовые файлы не получают ручной маркер Regression: SlopCodeBench классифицирует их как Regression автоматически при `include_prior_tests: true`.
- CP1 проверяет регистрацию, вход, хеширование пароля через отсутствие исходного значения в SQLite, начальные состояния, основные операции с задачами, изоляцию учетных записей, сохранность SQLite и запуск Uvicorn.
- CP2–CP6 проверяют проекты и Входящие, сроки, составные выборки, пользовательские состояния и устойчивый порядок канбан-доски через публичный API.
- CP7 проверяет успешное изменение по актуальной версии и неизменность данных при конфликте двух запросов.
- CP8–CP10 проверяют целостность ветви задач, обратимое удаление и неизменяемую историю, включая неделимость массовых операций.
- CP11–CP12 проверяют идемпотентную обработку точных сроков и календарные границы повторений на управляемом времени.
- CP13–CP15 проверяют аналитику на заранее построенных задачах и истории, включая пустые результаты, изоляцию учетных записей, совместимость сохраненных определений и точные ошибки недопустимых сочетаний.
- Эталонная реализация прогоняется после добавления каждого чекпоинта. Сначала должен проходить текущий Core и вся предыдущая Regression; затем проверяются Functionality и Error.
- До полного опыта отдельно запускается CP1. После появления запускаемой задачи выполняется обязательный smoke каждого измененного варианта, анализируются созданные им дополнительные файлы и исключаются только артефакты процесса, но не тесты агента.
- Полное сравнение выполняется несколькими повторами с параллельным запуском независимых прогонов. Один smoke или один полный прогон не считается итоговым научным результатом.

## Out of Scope

- Клиентская часть любого вида.
- Команды, общие рабочие пространства и совместное владение.
- Офлайн-режим, синхронизация, разрешение распределенных конфликтов и несколько источников истины.
- Внешние очереди и планировщики, email, push, webhooks и сторонние службы уведомлений.
- Необратимое удаление проектов или задач.
- Зависимости между задачами, отличные от дерева родитель—потомок.
- Автоматическое завершение потомков вместе с родителем.
- Восстановление текущего состояния из истории событий и отмена изменений по журналу.
- Повторение целой ветви задач.
- Произвольный SQL, пользовательские формулы и сохраненные снимки результатов отчетов.
- Единый взвешенный показатель качества.
- Изменение раннера SlopCodeBench или существующей задачи `file_backup`, если стандартные точки расширения достаточны.
- Оптимизация для высокой нагрузки, нескольких процессов записи или распределенной базы данных.

## Further Notes

- Предметный словарь и архитектурное решение являются источниками истины. В заданиях следует употреблять «учетная запись», «Входящие», «пользовательское состояние», «системная категория», «ветвь задач», «точный срок», «экземпляр повторения» и «сохраненный отчет» в зафиксированном смысле.
- Самый близкий существующий образец REST-задачи — `trajectory_api`: данные случаев, сохранение значений между шагами и проверка JSON-схем. Для запуска процесса полезны приемы `execution_server` и `dynamic_config_service_api`. Прямого существующего образца ASGI TestClient, JWT и управляемых часов в проверочных тестах нет, поэтому эти договоры вводятся этой спецификацией.
- До создания каркаса нужно сверить фактический формат закрепленных версий `trajectory_api` и `execution_server`. Новая задача создается отдельно; vendored `file_backup` не изменяется.
- Трекер задач и словарь его меток в репозитории не настроены. Этот документ подготовлен для публикации как одна задача с меткой `ready-for-agent`; публикация требует адреса проекта или настройки удаленного репозитория.
